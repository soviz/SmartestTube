## Instant Local Update After Edit/Delete — No Manual Refresh

Whenever a screen edits or deletes an object it's showing (a list item, a
detail view, a card), the on-screen state must reflect that change on the
same frame the edit/delete completes — never rely on the user pulling to
refresh or navigating away and back to see the result.

Concretely:
- The screen holding the list/object must splice the edited/deleted item
  into its local state as soon as the save/delete call returns with the
  persisted result — do not just call a network re-fetch (e.g. re-querying
  Supabase) and hope it already has the new row. Background sync (e.g. an
  offline-first repository's `_syncToCloud`) can lag the local save by a
  network round trip, so a re-fetch immediately after saving can silently
  show stale data or even lose the just-made change.
- Pattern: the mutating call site (form screen, edit sheet, delete handler)
  already has the freshly-saved/deleted object or id in hand — pass it back
  to the parent (via a returned value, callback, or similar) and have the
  parent update its local list/state directly (update-in-place by id, or
  remove by id), instead of triggering a full reload.
- If a full reload is already in flight when the optimistic update lands
  (e.g. the screen's initial load hasn't finished yet), guard against the
  stale reload overwriting the fresh optimistic state — e.g. a monotonic
  generation counter bumped on every optimistic update, with any in-flight
  reload checking it's still the current generation before applying its
  result.
- This applies regardless of how many entry points can trigger the edit
  (e.g. an inline form button vs. a detail bottom sheet reached by tapping
  a card) — every entry point must feed the same instant-update path, not
  just the "primary" one.

## Platform Admin Has Unconditional Access — Design For It From the Start

A platform superadmin (`profiles.is_admin`) always has full access to every
current and future user-facing feature that has its own permission model
(communities, catches, comments, challenges, and anything added later) —
create, read, update, delete, moderate, bypass any rank/threshold/
membership gate — regardless of whether they're a member/owner/participant
of the specific resource. This is a standing architectural requirement, not
a one-off request to bolt on after a feature ships.

Concretely, when designing or extending ANY permission-gated feature:
- **RLS is the real boundary — add the bypass there, not just client-side.**
  Every RLS policy that gates INSERT/UPDATE/DELETE (and usually SELECT) by
  role/rank/ownership/membership/threshold must also OR in the explicit
  check `EXISTS (SELECT 1 FROM public.profiles p WHERE p.id = auth.uid()
  AND p.is_admin = true)`. A client-side-only admin affordance with no
  matching RLS branch is not a real bypass — see
  `20260916180000_superadmin_community_bypass.sql`,
  `20260916190000_superadmin_catches_comments_bypass.sql`, and
  `20260916230000_superadmin_challenge_bypass.sql` for the established
  pattern (one new OR branch per policy, never a rewrite of the existing
  logic for everyone else).
- **The admin bypass must never grant a normal-user privilege escalation
  path.** It's an explicit `is_admin` check, not auto-membership/auto-
  ownership of the resource (e.g. an admin acting in a community they
  don't belong to does NOT get inserted into `community_members` — see the
  community bypass migration's header comment for why: it would silently
  distort member_count/leaderboards). Model it the same way for every new
  feature: a parallel OR condition, not a role grant.
- **Client-side gates need the same fallback.** Any widget that hides an
  action behind `myRole?.canX ?? false` (or similar per-resource role
  check) must also show it when `AdminService.isAdminSync()` is true, even
  when the admin has no role on that resource at all (`myRole == null`) —
  see `community_detail_screen.dart`'s `canManageMembers`/`canCreate`
  (challenge section) for the pattern: `isAdmin || (role != null &&
  role.canX)`. A threshold gate (e.g. the challenge feature's 10-member
  minimum) must also be skipped for the admin, not just the role check.
- **Every new SECURITY DEFINER function or RPC that reads/writes
  permission-gated data** should be re-audited for this the same way it's
  audited for the RLS-bypass risk described later in this file — decide
  explicitly whether the admin bypass needs to apply there too, don't
  assume it's inherited for free.
- Test the bypass locally the same way every other RLS change is tested
  (see "Test Before Deploy" below): an attack-scenario script proving a
  non-admin is still rejected AND the admin succeeds even when not a
  member/owner/participant and even under any threshold — save both as
  permanent regression tests.

### Visual Personality
Vobbl is a **field tool for anglers**, not a lifestyle app.
The visual language evokes:
- Deep lake water and morning mist → teal/navy primary tones
- Golden-hour fishing → amber accents for achievements and highlights
- Canadian wilderness → forest green for ecological context
- High-contrast readability in bright sunlight and dark boat cabins

Avoid decorative gradients, shadows, or animations that slow common workflows.
Prioritize readability and touch target size over visual novelty.

### Fixed Size Regardless of State

A widget's box size (button, select, text field, chip, card, icon slot, etc.) must
never change based on its status (selected/unselected, filled/empty, focused,
loading, error, etc.). A changing size shifts the widget itself and its siblings,
which reads as visual jitter. This applies to width, height, padding, border
width, and font size alike — not just borders.

Concretely:
- Never vary `Border.all(width: ...)` by state. Keep `width` constant and express
  state through `color`/opacity instead. If stronger emphasis is genuinely needed,
  use a fixed-width outline plus a subtle `boxShadow`/background tint.
- Never vary `padding`, `fontSize`, or icon `size` between states of the same
  slot (e.g. a leading icon that's larger when "filled" than when "empty").
  Reserve a fixed-size `SizedBox`/`Center` for any slot whose content changes
  (icon vs. spinner vs. nothing) so the slot itself never resizes.
- When content length varies (e.g. a name vs. a placeholder), keep the same
  text style for both and let `Expanded`/`Flexible` + `overflow: ellipsis`
  absorb the difference — don't compensate by changing font size per state.
- Before shipping a stateful widget with visual variants, mentally render both
  states side by side and confirm the bounding box is identical.

### Animate Show/Hide — No Hard Cuts

Any block whose visibility toggles at runtime (validation errors, warnings,
conditional sections, badges, empty-state swaps) must fade and/or resize in
and out smoothly. A block that appears or disappears on a single frame reads
as a layout jump, not a state change.

Concretely:
- Never gate a widget with a bare `if (cond) Widget(...)` / `if (cond) ...[...]`
  inside a `Column`/`ListView` when that condition can flip at runtime — the
  widget and everything below it will jump instantly. Keep the widget in the
  tree and animate `AnimatedOpacity` (fade) wrapped in `AnimatedSize`
  (height/width collapse) instead, ~150–250ms, `Curves.easeOut`.
- When both variants have very different intrinsic size (e.g. an error line
  vs. nothing), still branch on the condition for the *content*, but always
  render it inside the same `AnimatedSize`/`AnimatedOpacity` pair so the
  transition itself animates, not just the endpoints.
- List insertions/removals (e.g. removing a photo from a gallery) should
  animate out (opacity + size collapse) before the item leaves the
  underlying data list — don't call `setState` that removes the item on the
  same frame as the tap; animate first, then remove after the animation
  duration elapses.
- This does not apply to screen-level navigation transitions (those already
  animate via the platform's route transition) — it applies to widgets
  appearing/disappearing *within* an already-visible screen.

### Loading States Need a Skeleton Placeholder, Not a Blank Gap

Any widget/section whose content depends on an async fetch (network,
reverse-geocoding, a Supabase query, anything that isn't available on the
first frame) must show an animated skeleton placeholder — a pulse or
shimmer over shapes that approximate the real content's layout — instead of
an empty `SizedBox.shrink()`, a plain spinner dropped into unrelated
layout, or (worst) surrounding elements (buttons, icons) rendering into the
gap and visually colliding before the real content arrives.

Concretely:
- Match the placeholder's shape to the real content's layout (e.g. a title
  bar + a shorter subtitle bar for a two-line text label) so there's no
  visible size/position jump when the real content swaps in.
- Reserve the same space the loading widget takes: wrap both the
  placeholder and the real content in one `Expanded`/fixed-size container so
  siblings (buttons, icons) never shift or crowd together while data is
  still loading — see the "Fixed Size Regardless of State" rule above.
- Animate the placeholder itself (an opacity pulse via `AnimationController`
  set to `repeat(reverse: true)`, or a moving shimmer gradient) rather than
  a static gray box — a static box reads as a rendering bug, not a loading
  state.
- Cross-fade from placeholder to real content (`AnimatedSwitcher`,
  ~200-250ms) instead of a hard cut, per "Animate Show/Hide" above.
- No new package is required for a simple pulse — a `Tween<double>` opacity
  animation over a `Container` with rounded corners is enough; reach for a
  shimmer-gradient package only if a moving-highlight effect is specifically
  wanted.
- Applies to first-load AND to switching to new data mid-session (e.g.
  re-resolving a place name after the user picks a new location) — anywhere
  a gap between "old/no content" and "new content" would otherwise be
  visible for more than a frame or two.

## Badge Hints — Unit-Aware Measurements

Storage for badge condition values is always metric (`BadgeModel.conditionValue`
in kg / cm / km/h / °C / m — see `lib/core/gamification/badge_model.dart`).
Display must respect the user's metric/imperial preference
(`lib/core/utils/unit_converter.dart`, `UnitConverter`), the same way catch
logging and catch detail screens already do.

When creating a NEW badge whose hint text mentions a weight, length,
temperature, wind speed, or altitude threshold:
- Do NOT bake a hardcoded unit string (e.g. `"5 kg"`, `"90 cm"`) into the
  `.arb` hint string for any language.
- Add an ICU placeholder instead (e.g. `"Catch a fish weighing {weight} or
  more."`) to `lib/l10n/app_en.arb` (with a `placeholders` block) and to the
  translated string in `app_es.arb` / `app_fr.arb` / `app_ru.arb` /
  `app_zh.arb`.
- Manually mirror the placeholder in the generated
  `lib/l10n/app_localizations.dart` (abstract getter → method) and each
  `lib/l10n/app_localizations_<lang>.dart` (since `flutter gen-l10n` is not
  run for you — see Core Principles).
- Add a case for the new badge ID at the top of `BadgeL10n.hint()` in
  `lib/core/gamification/badge_l10n.dart`, calling the matching
  `UnitConverter.format*` helper (`formatWeight`, `formatLength`,
  `formatTemperature`, `formatWindSpeed`, `formatAltitude`) with the badge's
  `conditionValue`.
- If the new badge needs a measurement type `UnitConverter` doesn't format
  yet (e.g. distance in km/mi), add a `display*`/`format*` pair there first,
  following the existing pattern (metric storage, `isImperial` branch).

## Adding a New Fish Species — All Call Sites Must Be Updated

The species catalog (`lib/core/constants/fish_species.dart`, `kAllFishSpecies`)
is the single source of truth every species picker, autocomplete, and map pin
icon reads from directly — but two of its own pieces are NOT compiler-checked
against the list and silently degrade (unlocalized name, `unknown.png` icon)
if forgotten. `fish_type` itself is unrestricted free text in Supabase (no
CHECK constraint/enum), so nothing needs to change there.

When adding a new species, do ALL of the following — none of these produce a
compile error if skipped, so it's easy to ship a half-added species:

1. Add a PNG to `assets/images/fish_icons/` — lowercase, spaces/hyphens
   replaced with underscores (e.g. `'White Sucker'` → `white_sucker.png`,
   `'Mahi-Mahi'` → `mahi_mahi.png`; see `FishSpecies.iconPath`). No `pubspec.yaml`
   change needed — `assets/images/fish_icons/` is already a whole-folder
   include. Must be a white/transparent silhouette (or get recolored via
   `ColorFilter` at the one call site that composites it onto a red map pin
   in `map_screen.dart`'s `_getCatchMarkerImage`) — check how it reads
   composited on that pin, not just standalone.
2. Add a `FishSpecies(name: ..., iconAsset: ...)` entry to `kAllFishSpecies`
   in `lib/core/constants/fish_species.dart`.
3. Add a matching case to the `localizedFishName()` switch in the same file
   (`'NewSpecies' => l10n.fishSpeciesNewSpecies,`) — skipping this makes the
   new species silently fall back to its raw English name in every locale
   instead of being translated.
4. Add a `"fishSpeciesNewSpecies"` key (+ `@fishSpeciesNewSpecies` metadata
   block) to **all five** `.arb` files — `app_en.arb`, `app_es.arb`,
   `app_fr.arb`, `app_ru.arb`, `app_zh.arb` — with a real translation in
   es/fr/ru/zh, not copy-pasted English.
5. Run `flutter gen-l10n` yourself (allowed per Core Principles) so the
   `l10n.fishSpeciesNewSpecies` getter referenced in step 3 actually exists.
6. Add a `"NewSpecies": { ... }` entry to `assets/data/fish_profiles.json`
   (`water`, `rarity`, 6 radar stats 0..10, an `activity` archetype, 12
   season values, temp/depth ranges, `pressure_pref`, `light_pref`, weights,
   `lures`) — see `docs/FISH_PROFILES.md` for the stat calibration rubric.
   `desc_key`/`tip_keys` are required for every species, not just a top-12
   subset — leaving them `null`/`[]` makes the species sheet silently skip
   those sections with no placeholder text, and every other species in the
   catalog already has them filled in, so a gap there is inconsistent, not
   optional. Add the description/tip strings (+ `@meta` blocks in
   `app_en.arb` only) to **all five** `.arb` files with real translations in
   es/fr/ru/zh, matching the tone of existing entries for the same water
   type. Skipping the `fish_profiles.json` entry entirely doesn't break the
   build either — `FishProfileLoader` silently omits the species from the
   catalog's stats/radar/activity sections — so run "Validate fish profiles"
   in the admin debug panel after adding a species to confirm the entry is
   actually there.
   `test/fish_catalog/fish_profiles_data_test.dart`'s "every species has
   desc_key" test checks this with no hardcoded species count (it asserts
   zero entries are missing `desc_key`, not `withDesc == 42/43/...`) — so
   adding a species with `desc_key` filled in needs no test edit. Never
   reintroduce an `expect(withDesc, <N>)`-style count in that file; it just
   forces a manual bump on every new species and breaks CI for an unrelated
   reason.
   Separately, `desc_key`/every `tip_keys` entry also needs a matching case
   added to the `_resolveDesc()`/`_resolveTip()` switches at the bottom of
   `lib/widgets/fish_species_sheet.dart` — these are plain string switches
   over the key, NOT resolved by reflection, and both fall back to
   `_ => key`, so a missing case doesn't crash or fail any test, it just
   silently renders the raw key literal (e.g. `"fishDescBluegill"`) on the
   species sheet instead of the translated text. The existing `.arb`
   coverage tests only check that the key exists in `app_en.arb`, not that
   this switch has a case for it — so this is a real gap the test suite does
   not catch; visually check the species sheet after adding a species.
   - `"rarity"` is one of `"common"` / `"uncommon"` / `"rare"` / `"epic"` /
     `"legendary"` — drives the species sheet's backdrop-glow color (see
     `fishRarityColor()` in `lib/features/fish_catalog/presentation/widgets/
     fish_rarity_colors.dart`) and the catalog grid tile's border/fill tint
     (`FishGridTile`). Shares the exact same 5-tier palette as
     `BadgeRarity`/`AppColors.rarity*` — never introduce a new hex value for
     a fish rarity tier, reuse the existing tokens so "rare" reads as the
     same color everywhere in the app. Missing `rarity` fails
     `test/fish_catalog/fish_profiles_data_test.dart` (defaults to `common`
     at runtime via `FishProfile.fromJson`, but the test enforces it's
     always set explicitly).
   - Pick the tier editorially — weigh `stats.abundance` (inverse: low
     abundance leans rarer) together with `stats.trophy` and `record_weight`
     (high trophy/record leans rarer even if not scarce), not a mechanical
     abundance-only formula. Rough anchors from the current 43-species set:
     common = abundance 8-10 & trophy ≤5 (e.g. Bass, Perch, Sunfish); rare/
     epic = abundance 2-5 with elevated trophy (e.g. Halibut, Tuna, Shark);
     legendary = abundance 1 and/or trophy 9-10, the handful of
     genuinely mythic-tier catches (Muskie, Sturgeon, Marlin, Swordfish,
     Tarpon) — keep legendary rare across the whole catalog, not just
     "the biggest version of a common fish."

Optional, only if wanted for this specific species (not required):
- A species-specific badge (`lib/core/gamification/badge_registry.dart`'s
  `specificSpeciesCount` badges + matching name/hint cases in
  `badge_l10n.dart`) — most species have no dedicated badge and don't need
  one.
- A per-species trip-planner tackle entry in
  `assets/data/trip_tackle_matrix.json` (keyed `speciesKey+method`) — falls
  back to a `generic+method` entry automatically if absent.

## Adding a Premium (Pro-only) Feature — Always Add a Paywall Slide

`PremiumScreen` (`lib/features/settings/presentation/premium_screen.dart`)
sells every Pro feature through a full-bleed image carousel (`_FeatureSlide`,
`_assetPaths`, `_slideCount`) with a localized title per slide (`_slides()`,
`_SlideContent`). A Pro feature that isn't listed there is invisible at the
point of purchase — the user pays without knowing it exists, then discovers
it later inside the app. That gap is exactly the "bait and switch" failure
mode: don't gate a new capability behind `SubscriptionService.isPremiumNotifier`
without also advertising it on the paywall in the same change.

When adding a new Pro-gated feature:
1. Bump `_slideCount` by one.
2. Add a `_SlideContent(title: l10n.premiumBenefit<Name>Title)` entry to
   `_slides()`, and the matching `"premiumBenefit<Name>Title"` key (+ `@meta`
   block in `app_en.arb` only) to **all five** `.arb` files, with real
   translations in es/fr/ru/zh — then run `flutter gen-l10n`.
3. Add a matching entry to `_FeatureSlide._assetPaths`
   (`assets/paywall/<N>.jpeg`) even though the real screenshot asset doesn't
   exist yet — `Image.asset`'s `errorBuilder` automatically falls back to
   `_SlideGlow(index: N)`, an abstract gradient composition, so the slide
   renders correctly on dev with just the title until a real screenshot is
   designed and dropped in later. Do NOT skip the slide waiting for the
   asset — the fallback is the intended mechanism for exactly this gap, not
   a hack to avoid.
4. Add one more layout (a couple of `_blob(...)` calls) to the `layouts` list
   inside `_SlideGlow.build()` so the fallback for the new index looks
   distinct from the others, not a repeat via `index % layouts.length`.

## Supabase Migration Filenames — Unique Timestamps Required

The Supabase CLI identifies each migration by the numeric prefix before the
first `_` in its filename (e.g. `20260714` in `20260714_foo.sql`), and
tracks applied migrations by that exact prefix in
`supabase_migrations.schema_migrations`. Two files sharing a prefix are
indistinguishable to the CLI — this has broken `supabase db push` more than
once (`duplicate key value violates unique constraint
"schema_migrations_pkey"`, or a repair silently no-op'ing on the wrong file)
and required manual `supabase migration repair --status applied/reverted`
surgery to untangle.

When creating a new migration file:
- **Always include a time component** in the prefix, not just the date:
  `YYYYMMDDHHMMSS_description.sql` (e.g. `20260714093000_add_foo_column.sql`),
  even if several migrations land on the same calendar day. Never reuse a
  bare `YYYYMMDD_description.sql` prefix if another migration already uses
  that same date-only prefix.
- Before naming a new file, run `ls supabase/migrations/ | grep <today's
  date>` (or check `supabase migration list`) to see what prefixes already
  exist that day, and pick a later time so ordering stays correct relative
  to any dependencies between them.
- If you ever do end up with a genuine prefix collision (e.g. from a rebase
  or two people working in parallel), rename the files to unique
  `YYYYMMDDHHMMSS` prefixes *before* running `supabase db push` — don't
  push first and try to repair around the error.

## Test Before Deploy — SQL Locally, Dart Logic in `test/`

Verification for both SQL migrations and non-trivial Dart logic changes
must happen *before* the change is considered done — not deferred to "the
user will test it in the app." This discipline has caught real bugs
(privilege escalation, infinite RLS recursion, a SECURITY DEFINER function
silently bypassing an age/strike gate RLS enforced elsewhere, a pagination
bug that skipped real feed items) that `flutter analyze` and a clean test
run both missed on their own.

### SQL migrations (RPCs, RLS policies, trigger functions)

1. Test every new/changed migration against a local, isolated Postgres
   (`supabase db reset`) before pushing to dev — never push straight from
   reading the SQL.
2. Write actual attack scenarios, not just the happy path: self-escalation
   attempts, cross-tenant reads (can a non-member see a private resource),
   bypassing a rate/age/strike gate through a different code path than the
   one RLS protects, a lower-privileged role attempting a higher-privileged
   action. Simulate callers with `SET LOCAL role authenticated;` +
   `SET LOCAL request.jwt.claims = '{"sub":"<uid>","role":"authenticated"}';`
   (or `SET LOCAL role service_role;`) inside `BEGIN ... COMMIT/ROLLBACK`.
3. **`SECURITY DEFINER` bypasses RLS entirely** on every table it touches —
   if an RLS policy on a table enforces some invariant (an age gate, a
   strike/ban check, a role-rank comparison) and a `SECURITY DEFINER`
   function also writes to or reads from that table, the RLS policy
   provides zero protection there unless the same check is explicitly
   duplicated inside the function body. Treat every new `SECURITY DEFINER`
   function as a fresh audit of "what RLS normally protects on these
   tables, and does this function re-check it."
4. Once every scenario behaves as expected, save the attack-scenario `.sql`
   script as a **permanent regression test in the repo** (not left in a
   scratchpad and discarded) — a later migration can silently reintroduce
   the exact same class of bug otherwise (this has already happened once:
   a migration reverted a previously-fixed SECURITY DEFINER/hardcoded-URL
   bug from an earlier migration). If no test directory convention exists
   yet for this, ask once, then keep using it for every future migration.
5. Only push to dev after local verification passes. Never push to prod
   without the user's explicit, scoped confirmation — a fix migration that
   "only touches one function" can still turn out to depend on a chain of
   prior migrations not yet on prod.

### Dart logic (not just SQL)

Whenever new or changed Dart logic is non-trivial — parsing/serialization,
pagination/offset math, ranking or interleaving logic, validation rules,
state machines — add or update a unit test in `test/` in the same change.
`flutter analyze` catches type errors, not logic errors; a clean analyze
and a passing existing suite are not evidence that new branching logic is
correct. Skip this for trivial getters, straightforward widget composition
with no branching, or a one-line pass-through to a repository/RPC call
(the RPC's own correctness is covered by the SQL regression tests above).

## Bumping the App Version Before a Play Store Upload

Google Play rejects any AAB upload whose `versionCode` is not strictly
greater than the highest `versionCode` already uploaded to that app,
across every track (internal/closed/open/production) — this isn't
automatic, `flutter build appbundle` just uses whatever is currently in
`pubspec.yaml`.

Before running `flutter build appbundle --flavor prod
--dart-define-from-file=dart_defines/prod.env` for an upload:

1. Bump the build number (the `+N` suffix) in `pubspec.yaml`'s `version:`
   line — e.g. `1.0.0+1` → `1.0.0+2`. Bump the version name (`1.0.0` part)
   too when the release is user-facing/significant, but the build number
   must go up on every single upload, no exceptions.
2. The Settings screen's version row
   (`lib/features/settings/presentation/settings_screen.dart`) reads the
   version live via `package_info_plus`
   (`PackageInfo.fromPlatform()` in `_loadAppVersion()`), not a hardcoded
   string — nothing to keep in sync by hand here anymore.
3. If unsure what the last uploaded `versionCode` was, check Play Console →
   the app → Testing/Release → the track you're about to upload to — it
   shows the version code of the most recent release on that track.

Note: this section is about the *installed build's* version. It's unrelated
to `app_versions` (the Supabase table backing the in-app update nudge — see
`lib/core/services/app_update_service.dart`), which the Release (Android)
workflow's "Sync app_versions (latest version)" step keeps in sync
automatically after every push-to-main upload — no manual DB edit needed for
`latest_version_code`/`latest_version_name`. The one field that step
deliberately never touches is `min_supported_version_code` (the forced-update
floor) — raising that is still a manual decision: set it equal to
`latest_version_code` during closed testing to force every tester onto the
newest build, and leave it behind in normal production releases so only the
dismissible soft nudge fires.

## Changelog & Release Notes (`CHANGELOG.md`)

`CHANGELOG.md`'s `## Unreleased` section is what actually ships as the
Play Store "what's new" text: on every push to `main`, the Release
(Android) workflow (`.github/workflows/release.yml`) reads that section,
uploads it as the internal-testing release notes, then rewrites the file —
renaming `## Unreleased` to `## <version>+<build>` and committing a fresh
empty `## Unreleased` back to `main`. If the section is empty at push time,
Play gets no release notes for that build, so keep it filled in as you go
rather than writing it all right before a release.

- Whenever a change you make is user-facing (a new feature, a fix a user
  would notice, a behavior change) — not internal refactors, CI tweaks, or
  code cleanup — add a one-line bullet to `## Unreleased` in the same
  response that makes the change, in plain language a non-technical angler
  would understand (not the commit message or the internal
  file/function-level description).
- Immediately before a push to `main` (i.e. once the user confirms they're
  ready to deploy), review the accumulated `## Unreleased` bullets and
  tighten them into a short, well-written release-notes paragraph or list —
  this is what testers will actually read in Play Console, so make it read
  like real release notes, not a raw changelog dump.
- Don't ask the user to maintain this file by hand — it's your job to keep
  it current as part of doing the feature work itself.
- The entire `## Unreleased` section — the whole text that ships as the Play
  Store "what's new" for that release — must never exceed 200 characters
  total. Keep bullets terse as you add them through development so the
  section doesn't balloon; if it's already over 200 characters by release
  time, tighten/merge bullets into a single short line (or a couple of very
  short ones) rather than trimming a few words off each — the 200-character
  cap is on the release as a whole, not per bullet.
